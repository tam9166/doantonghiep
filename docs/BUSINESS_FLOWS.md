# Business flows

Auth, forced password change, reservation/event booking, order/inventory, kitchen/waiter, table state, cashier/payment, voucher, review, staff/timekeeping, recruitment, AI, WebSocket, errors, browser navigation, DB migration, and deployment are tracked in `TEST_MATRIX.md`. Each change must identify affected flows before patching.

The 2026-08-20 continuation specifically reverified order classification/history, rate-limit profile safety, scheduled reservation expiry/no-show processing, customer/staff dual-session isolation, kitchen error feedback, Flyway legacy-data preflight, and the shared visual theme. `contact_task_status` remains documented technical/product debt and is not an active business flow.

The latest flow audit also covers payment-ledger cancellation/refund, five simultaneous window-scoped roles, delivery checkout, reservation auto-table/payment, configured business hours and Vietnam dates, event retry idempotency, table QR capabilities/add-more, structured kitchen/waiter/cashier order data, persisted order codes/schedules, waitlist privacy/concurrency, staff input validation, route resource cleanup, and synchronized generated frontend assets. See `MASTER_PROMPT_V2_FLOW_AUDIT_2026-08-20.md` for the evidence and remaining manual-browser verification.

Runtime continuation verified every exact Vue route against the packaged backend and fixed the shared SPA refresh registry. It also exercised the reservation expiry scheduler against SQL Server, fixing the `TIME`/`DATETIME` parameter mismatch that previously stopped no-show/expiry processing. Browser/API smoke then fixed the public hot-menu schema contract and removed the dine-in guest screen's dependency on an admin-only popular-items endpoint.

The 2026-08-21 cancellation flow now separates customer request, manager decision and externally confirmed refund. Verification requires any two of booking code, name, phone and email to match the same future/open reservation; the public response contains no reservation PII. Refund eligibility is snapshotted at request time using the Vietnam booking datetime and the net successful payment ledger. Contact attempts are append-only.

Menu availability uses FIFO batch totals as the stock source of truth and publishes a numeric recipe-limited serving count. Checkout now creates per-order/per-ingredient holds instead of immediately consuming batches. Active, unexpired holds reduce customer-visible servings; full ledger payment or authorized COD/tại-quán dispatch consumes FIFO stock once; cancellation and expired transfer intents release holds. Late transfer callbacks are retained for manual review and cannot dispatch an order after its hold expired.

Kitchen dish cancellation is now one transaction across detail, parent order, inventory and finance. A held dish reduces the hold; an already-consumed but not-started dish compensates recipe stock; a started dish is treated as waste and is not put back into sellable stock. The canceled line and tax are removed from the order, paid excess creates a pending—not completed—refund, and actor/reason/time are retained.

Operational order status now has one canonical state machine. Unknown numeric states and skipped transitions are rejected; kitchen completion derives partial/fully-ready parent states from active dishes. WAITER can only mark a completed dish as served, and the parent reaches SERVED only when every non-cancelled dish has been served.

Table composition is now fail-closed around money and stock. Merge/split is rejected once an order has payment allocation, refund, voucher or an active inventory hold; split validates every requested detail and requires an active target without another open order. Transfer locks and validates the target and revokes both QR capabilities. Direct release/unlink shares a guard that requires settled money and served dishes before closing an eligible paid order.

Event bookings now use the same secure deposit capability model as regular reservations. Creation records the authenticated owner and deposit expiry, returns a short-lived capability, notifies managers/realtime clients, and the event page immediately requests and displays the QR while preserving the booking if QR generation is temporarily unavailable. Dedicated CAPTCHA and rate limits protect the public create endpoint.

Attendance now serializes same-employee check-in, enforces one row per business date, evaluates lateness from the employee's persisted shift and records overnight-safe total hours at check-out. Kitchen updates remain WebSocket-first with a 60-second scoped fallback. Historical-growth-sensitive admin, revenue, waiter, kitchen, reservation, popular-item, purchase-suggestion and staff-assistant paths use bounded/status/date/active repository queries; complete lists remain only where the business result is itself the small reference/catalog set or during controlled startup validation/seed work.

Dangerous cashier, kitchen and table actions now use a shared nonblocking confirm/prompt dialog and global outcome toasts. Invoice, history invoice and shift-report printing clone content into an isolated iframe, preserving live Vue state. Recruitment submissions validate identity/message/post metadata before validating and privately storing an optional CV. Clean lockfile installation, dependency audit, Linux Maven-wrapper permissions and explicit logging for nonfatal fallbacks are part of the release verification contract.

Table availability now has one runtime writer: `TableLifecycleService`. It locks affected tables in ascending ID order, rejects unpaid/pending-payment/pending-refund/unserved/active-hold states, clears the table only after all invariants pass, and revokes its QR capability in the same transaction. Cancelling a paid order retains the table while the refund is pending; verified refund completion performs the release. Merge, split, transfer, reservation cancellation/no-show and manual status/unlink paths share this contract.

Merge, split and transfer acquire affected table/order locks deterministically. Reservation voucher consumption and waitlist terminal transitions also lock their mutable records. Capacity and automatic table assignment compare complete `LocalDateTime` intervals and include previous-day reservations that continue past midnight.

Waitlist conversion now requires an existing reservation that matches the customer's phone, booking date, guest count and selected area. The reservation row is locked during conversion, and V059 guarantees that two waitlist entries cannot claim the same reservation even under concurrent requests.
